# Realtime transcription protocol

This server implements the GA transcription subset over an authenticated
WebSocket at `GET /v1/realtime?intent=transcription`. It uses configured local
transcription models and the same worker pool as `POST /v1/audio/transcriptions`.
There is no hosted OpenAI backend or conversational response mode.

## Connection and configuration

Use `Authorization: Bearer <token>`. Authentication, supported query parameters,
and client concurrency are checked before the upgrade. Failed upgrades use the
existing HTTP error envelope. A request without a WebSocket upgrade receives
HTTP 426 with `Upgrade: websocket` and `Connection: Upgrade`. The upgrade
response includes `X-Request-Id`.

The first event describes the effective session. IDs shown below are examples:

```json
{
  "type": "session.created",
  "event_id": "event_example",
  "session": {
    "id": "sess_example",
    "object": "realtime.transcription_session",
    "type": "transcription",
    "expires_at": 1791127200,
    "audio": {
      "input": {
        "format": {"type": "audio/pcm", "rate": 24000},
        "transcription": null,
        "noise_reduction": null,
        "turn_detection": null
      }
    },
    "include": []
  }
}
```

`expires_at` is the enforced session expiration in epoch seconds. Select an
authorized model with `session.update`:

```json
{
  "type": "session.update",
  "event_id": "configure_1",
  "session": {
    "type": "transcription",
    "audio": {
      "input": {
        "format": {"type": "audio/pcm", "rate": 24000},
        "transcription": {"model": "parakeet-local"},
        "noise_reduction": null,
        "turn_detection": null
      }
    }
  }
}
```

Success produces `session.updated` with the same complete effective session
shape. Its `event_id` is generated by the server. Clients wait for this event
before recording. Model IDs come from the authorized model catalog;
`model: "default"` resolves the configured authorized default and the response
contains its actual model ID. No configured default is needed when selecting an
explicit model.

Updates retain omitted settings. `session.type` must be `transcription`;
other supported settings are optional. Optional transcription `language` must
be supported by the model when it declares a language list. `prompt` requires
`supports_prompt: true`. Validation and authorization happen before applying
any change. Updates require an empty input buffer and no committed job.

An empty `prompt` string removes the prompt. Set
`session.audio.input.transcription` to null to disable transcription and clear
the selected model, language, and prompt together. Appending or committing is
then rejected until a later update selects a model. This allows a model switch
without inheriting hints the new model does not support. Omitted nested fields
retain their values during other updates; null or empty language strings are
not supported reset forms.

Only 24 kHz `audio/pcm`, null noise reduction, null turn detection, and an empty
`include` list are supported. Unknown fields, beta event aliases, conversational
sessions, server VAD, logprobs, provider extensions, and `response.*` fail with
an error event. The server does not require an `OpenAI-Beta` header.

## Audio and results

| Client event | Input | Server behavior |
| --- | --- | --- |
| `input_audio_buffer.append` | `audio`: canonical Base64 of mono signed PCM16LE at 24 kHz | Appends whole samples; no acknowledgment |
| `input_audio_buffer.clear` | No additional fields | Clears uncommitted audio and sends `input_audio_buffer.cleared` |
| `input_audio_buffer.commit` | No additional fields | Requires at least 100 ms, clears the input buffer, and starts one batch transcription |

Every client event may have a string `event_id` of at most 256 characters.
Binary WebSocket messages are unsupported. Invalid audio is rejected before
inference. Model duration and configured byte limits apply to each buffer.

The commit acknowledgment establishes ordering and result correlation:

```json
{
  "type": "input_audio_buffer.committed",
  "event_id": "event_committed",
  "item_id": "item_utterance",
  "previous_item_id": null
}
```

`previous_item_id` is null for the first commit and the preceding committed item
ID thereafter. Final success is:

```json
{
  "type": "conversation.item.input_audio_transcription.completed",
  "event_id": "event_completed",
  "item_id": "item_utterance",
  "content_index": 0,
  "transcript": "Recognized words",
  "usage": {"type": "duration", "seconds": 0.2}
}
```

Parakeet is a batch model, so this service emits only the final transcript. It
does not invent incremental deltas. Duration equals committed decoded PCM bytes
divided by 48,000. Input is staged as a 24 kHz WAV and normalized to the worker's
16 kHz mono WAV with configured ffmpeg.

One committed job may be pending per session. A second commit while it is
pending fails with `transcription_busy` and leaves the next input buffer intact.
Clearing that buffer does not cancel the committed job. A success or failure
event is sent after the job's worker reservation, model queue slot, and temporary
files have been released; the client can then commit another utterance.

## Failures and closure

Invalid requests use the standard Realtime error event. `error.event_id` is
present when the rejected client event supplied a valid event ID:

```json
{
  "type": "error",
  "event_id": "event_error",
  "error": {
    "type": "invalid_request_error",
    "code": "transcription_busy",
    "message": "Wait for the previous transcription before committing again.",
    "param": null,
    "event_id": "commit_2"
  }
}
```

Once a commit is acknowledged, normalization, queue, deadline, or provider
failures produce an item-correlated terminal event:

```json
{
  "type": "conversation.item.input_audio_transcription.failed",
  "event_id": "event_failed",
  "item_id": "item_utterance",
  "content_index": 0,
  "error": {
    "type": "transcription_error",
    "code": "request_timeout",
    "message": "Transcription timed out.",
    "param": null
  }
}
```

Closing the WebSocket aborts queued work and requests cancellation of inference.
It suppresses later transcript delivery. Synchronous local inference may finish
before it acknowledges cancellation; the session continues owning its admission
slot and model resources until the worker settles or the configured cancellation
grace forces worker recovery. The server provides no durable receipt or
idempotency guarantee for committed recordings. A client may make bounded
recognition retries after an uncertain outcome if it accepts repeated inference
and its cost; the server does not replay work
automatically after a transport failure.

## Resource limits

Authenticated `GET /v1/audio/capabilities` includes a required `realtime` object
on every permitted, enabled transcription model in `data`. Speech models do not
have this object. Its closed schema has these five required numeric fields:

```json
{
  "max_buffer_bytes": 5760000,
  "max_message_bytes": 1048576,
  "max_output_bytes": 1048576,
  "idle_timeout_seconds": 60,
  "max_session_seconds": 3600
}
```

`max_buffer_bytes` is a nonnegative even integer: the smaller of
`server.realtime.max_buffer_bytes` and the selected model's
`max_duration_seconds * 48000`, rounded down to a whole PCM16 sample. When a
model has no duration limit, only the server limit applies. The other fields
come directly from `server.realtime`: message and output limits are positive
integers, and time limits are positive seconds, potentially fractional, up to
2,147,483 seconds. Larger idle or session settings are rejected at startup
because Node timers would otherwise expire them immediately. Very
small configured model limits are reported as-is, including a zero-byte buffer
if the duration cannot hold one sample; discovery never raises a limit to make
a client usable. The WebSocket enforces the same effective buffer bound.

Clients should fetch capabilities for the exact selected model before starting
recording and compare them with their packet sizes, transcript bounds and
timing requirements. Picker caches do not establish current recording limits.
These are derived capability fields, not new operator configuration keys.

| `server.realtime` field | Default | Meaning |
| --- | --- | --- |
| `max_buffer_bytes` | 5,760,000 | 120 seconds of decoded PCM per buffer; lower model duration also applies |
| `max_message_bytes` | 1,048,576 | Maximum complete WebSocket JSON message |
| `max_output_bytes` | 1,048,576 | Maximum pending outbound data including the next event |
| `idle_timeout_seconds` | 60 | Idle connection deadline while no job is running |
| `max_session_seconds` | 3,600 | Session lifetime, including recording and inference |

The lifetime timer starts when the upgraded WebSocket session starts. Measuring
the advertised lifetime from immediately before the client opens its connection
gives a conservative deadline without relying on an HTTP `Date` header or the
client wall clock. Renew between independently tracked recognition jobs when
the remaining lifetime cannot accommodate another job. A disconnect or expiry
does not prove a committed job was unused; any client retry is a new recognition
attempt and may repeat inference. Idle time is reset by
received application messages, including audio appends, rather than WebSocket
pings; it pauses while a committed job runs.

At most one committed buffer and one new input buffer exist per session. Client
concurrency is shared with HTTP, and model queues limit media processing and
inference. Buffer overflow sends `audio_buffer_overflow` and closes with code
1009; oversized messages or output also close with 1009. Idle and expiration
close with 1000. Shutdown cancels sessions and sends close code 1001, with a
one-second forced teardown deadline for unresponsive sockets.
Inference uses `request_timeout_seconds`; normalization and worker cancellation
use their existing configured deadlines. Audio exceeding a limit fails
explicitly and is never silently truncated.

Normalization limits the output to the committed PCM duration at 16 kHz plus
bounded WAV overhead; the HTTP `max_upload_bytes` setting does not limit this
Realtime path. Because the server creates the canonical WAV input, decoder or
output-limit failures on this path are server faults (`normalization_failed`),
not client upload errors. Normalization deadlines retain `normalization_timeout`.
Unexpected failures and deadlines are logged using the HTTP
request ID, session ID, committed item ID, processing phase, and error
classification. These diagnostics exclude raw errors, audio, transcripts,
credentials, and client events.

Clients own VAD, silence, no-speech and capture deadlines. The server's bounds are
resource limits rather than speech-detection decisions.
